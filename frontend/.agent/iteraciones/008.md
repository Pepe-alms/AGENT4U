# Iteración 008 — T05 Núcleo del chat | HECHA

Fecha: 2026-10-03. Rama: `featue/merge`, **sin commits**.

## Constructor

1. **`features/chat/estado.ts`**: reducer **puro y exportado**. Ninguna llamada a
   red, ningún temporizador, ningún acceso al DOM. Toda la lógica del chat vive
   ahí porque el riesgo real está en el orden de los eventos del stream, y así
   se puede probar sin React.
2. **`useConversacion`**: conecta el reducer con el `AsyncGenerator` de
   `shared/api/preguntar`. Detalles que importan:
   - El id del hilo vive también en una `ref`, para que `enviar` no dependa del
     estado y mantenga su identidad entre renders.
   - Si el stream se cierra **sin evento terminal** (proceso caído a mitad) se
     despacha `fin`; sin eso, `enviando` se quedaría en `true` para siempre.
   - Al desmontar se aborta: si no, el lector sigue vivo despachando sobre algo
     que ya no existe.
3. **`Composer`**: autoexpandible en `useLayoutEffect` (en un efecto normal se
   vería el salto de una línea a dos). Enter envía, Shift+Enter salta, y se
   ignora mientras el IME está componiendo: si no, escribir en japonés o chino
   enviaría a medias.
4. **`Mensaje`**: burbuja con gradiente para el usuario, texto corrido para el
   agente, cursor de escritura, citas como insignias. `aria-live="polite"` y
   `aria-busy` mientras llega: sin eso el streaming es invisible para un lector
   de pantalla.
5. **`PanelChat`**: **posee su propio scroll**. El auto-scroll solo actúa si el
   usuario estaba pegado al fondo (margen de 80 px); si había subido a leer, el
   texto nuevo no le mueve la vista.
6. **`PanelFuentes`**: el panel derecho muestra nombre, sección y páginas de las
   fuentes del último mensaje que las tenga.

### Devolución 1 (resuelta)

El Validador recibió por props el contenedor con scroll del shell y lo mutaba.
`oxlint` lo marcó, con razón. Se corrigió moviendo la propiedad del scroll al
propio `PanelChat`, que además es mejor: el composer deja de irse con el hilo y
el shell no tiene que exponer refs.

### Devolución 2 (resuelta) — un fallo de UX real

Con el modelo fallando a mitad, el reducer conservaba el texto parcial pero
**descartaba el motivo**: el usuario veía la respuesta cortada sin saber por
qué. Se añadió `motivoError` como campo propio del mensaje, y la UI enseña las
dos cosas: lo que se llegó a escribir y "La respuesta se cortó: …".

## Tres artefactos de medición, por si vuelven a aparecer

Esta iteración se fue casi entera en diagnosticar fallos que **no existían**:

1. **El Vite nuevo no arrancaba** porque el puerto seguía ocupado por uno
   anterior, así que se estaba sirviendo código viejo. Siempre comprobar el log
   de arranque, no solo que el puerto responda.
2. **El stub SSE con `Transfer-Encoding: chunked` escrito a mano** funcionaba
   con `curl` pero colgaba al navegador. Con HTTP/1.0 y cierre al final va bien.
3. **`--virtual-time-budget` vuelca el DOM antes de que llegue la red real**: el
   reloj virtual corre mientras el servidor responde en tiempo real. Por eso
   parecía que el texto no llegaba nunca.

La solución que funcionó, y que conviene reutilizar: **un buzón de resultados**.
El probe hace `POST /resultado` al stub con lo que ha medido y se lee el fichero
después. Así la medición no depende de cuándo decida Chrome volcar el DOM.
